雙星座融合訊號

同一個 I/Q 串流裡同時包含 GPS 與北斗訊號，接收機可以一次捕獲兩個系統。

  • 為什麼是這兩個系統：北斗在亞太上空的衛星數量最多，GPS 則是全球最普及的系統；兩者合用，台灣上空可用的衛星大幅增加，定位幾何也更好。
  • GPS L1 C/A：1575.42 MHz，測距碼 1.023 Mcps（1023 碼片、週期 1 ms），LNAV 導航電文 50 bps。
  • 北斗 B1I：1561.098 MHz，測距碼 2.046 Mcps（2046 碼片、週期 1 ms）；目前支援 MEO／IGSO 的 D1 電文（50 bps，含 NH 二次碼）。
  • 兩系統各自保有發射時間與導航電文，但共用同一條取樣時間軸，幾何與時間對兩者一致。
  • 混合模式的最低取樣率設定為 20.8 Msps，足以同時涵蓋兩個載波頻率。
完整說明：03 訊號 →

16 通道即時並行基帶合成

16 顆衛星的訊號同時計算並疊加，生成速度跟上取樣時鐘，直接串流到 SDR 發射。

  • 每個通道各自維護碼相位、載波相位、都卜勒與導航電文位元，最後累加成一路複數基頻 I/Q。
  • 即時串流：依真實廣播星曆持續計算訊號，連續送入 SDR（UHD）發射。
  • 發射緩衝不能中斷：一旦斷流，真實接收機的鎖相與延遲鎖定迴路就會失鎖。
  • 16 路訊號疊加會提高峰值，需控制振幅定標，避免數值溢位或量化不足。
完整說明：05 即時 →

1 ms 碼同步生成區塊

GPS C/A 與北斗 B1I 的測距碼週期剛好都是 1 ms，因此以 1 ms 作為生成單位。

  • 每個區塊都包含完整的碼週期，碼相位與累加邊界自然對齊。
  • 每個區塊開始時更新衛星位置、傳播延遲與都卜勒，再一次產生該區塊的所有樣本。
  • 一個 50 bps 導航位元長 20 ms，正好是 20 個區塊，位元邊界與區塊對齊。
完整說明：02 流程 →

異質運算架構：CPU＋GPU

CPU 負責導航與模擬控制，CUDA GPU 加速大量 I/Q 訊號生成。

  • CPU：讀取與篩選 RINEX 星曆、處理時間與座標轉換、計算衛星軌道／時鐘／偽距、挑選可見衛星並更新通道狀態。
  • GPU（CUDA）：平行產生各衛星通道的基頻 I/Q 樣本，再把多通道訊號合成輸出。
  • CPU 也負責 GUI、資料佇列、檔案輸出，以及需要時的 USRP 串流管理。

01

為什麼要把天空搬進實驗室？

重點真實天空每次都不同；GeoTrust 以真實廣播星曆重建衛星訊號，讓同一片天空能可控地重現。

戶外實測難以重現

天氣、遮蔽、多路徑與衛星位置每次都不同，同一個演算法很難在相同條件下比較兩次。

真實衛星無法控制

無法指定可見衛星數量、移動路徑，或刻意製造異常情境來檢驗接收機的反應。

GeoTrust 讓天空可控

以真實廣播星曆重建衛星訊號，可指定接收位置與路徑；相同設定可重新生成，讓測試可重現、可比較。

深入了解
  • 可重現的定義：記錄星曆版本、起始時刻、移動路徑、取樣率與通道數，就能重新生成同一組 I/Q。
  • 可控的意義：可以指定觀測地點、時段與路徑，甚至在播放中即時改變情境，這是戶外實測做不到的。

下一個問題03一顆衛星的訊號長什麼樣？↓
03

一顆衛星的訊號長什麼樣？

重點訊號＝導航資料 × 測距碼 × 載波；接收機靠測距碼找出延遲，再換算成距離。

50 bps · 每位元 20 ms

導航資料

導航電文以每秒 50 位元播送，內容包含星曆、時鐘修正與時間資訊。圖中高低代表 ±1 的位元符號。

1.023 / 2.046 Mcps · 週期 1 ms

測距碼

每顆衛星有專屬的偽隨機碼。接收機以相關運算找出碼的起點，得到訊號延遲，進而換算距離。

L1 1575.42 · B1I 1561.098 MHz

載波

資料與碼決定訊號的正負號，載波以連續相位承載它們；衛星運動造成的都卜勒會讓頻率略為偏移。

多衛星疊加

合成 I/Q

每個通道各自產生訊號後，在同一時刻相加成一路複數基頻 I/Q。真實的單一衛星訊號遠低於雜訊，需要相關運算才能取出。

示意波形：時間軸經過縮放，非實測訊號。

深入了解
  • 訊號非常微弱：GPS L1 C/A 在地面的規格最低接收功率約 −128.5 dBm，低於熱雜訊，必須靠相關運算長時間累積才能取出。
  • 兩個系統的差異：GPS C/A 碼 1023 碼片、北斗 B1I 碼 2046 碼片，週期都是 1 ms；北斗 D1 電文另外疊加 NH 二次碼。

04

16 顆衛星怎麼同時算？

重點CPU 算「衛星在哪裡」，GPU 算「訊號長怎樣」；分工之後，預設 16 個通道並行生成，硬體足夠時還能再增加。

CPU導航與控制

  1. 讀取與篩選 RINEX 星曆
  2. 時間與座標轉換
  3. 軌道、時鐘與偽距計算
  4. 挑選可見衛星、更新通道狀態
通道參數

GPUCUDA 平行生成

16 個通道同時計算碼、載波與電文，累加為一路 I/Q。

I/Q 區塊

OUT輸出與管理

  • USRP 即時串流（UHD）
  • I/Q 檔案
  • JSON 紀錄
  • GUI 與資料佇列（CPU）
深入了解
  • 為什麼這樣分工：導航計算每 1 ms 只需更新少量參數，邏輯複雜但資料量小，適合 CPU；I/Q 樣本每秒數百萬到數千萬筆且彼此獨立，適合 GPU 平行處理。
  • 兩端以資料佇列銜接：CPU 送出各通道參數，GPU 回傳 I/Q 區塊，彼此不互相等待。

05

為什麼必須準時送出？

重點SDR 以固定取樣時鐘發射；只要晚一步，緩衝耗盡，接收機就會失鎖。

GPU
發射緩衝
SDR
GPS 最低取樣率設定2.6 Msps單一星座 L1 C/A
北斗最低取樣率設定5.2 Msps單一星座 B1I
混合模式最低取樣率設定20.8 Msps同時涵蓋兩個載波
深入了解
  • 區塊長度與 C/A、B1I 碼週期相同（1 ms），碼相位與導航位元邊界自然對齊。
  • 每個樣本都依真實星曆即時算出，串流途中仍可改變接收位置與路徑。
  • 一旦緩衝耗盡（underflow），訊號中斷，接收機的鎖相與延遲鎖定迴路就會失鎖。上方取樣率為平台設定值，不是所有接收機的通用需求。

06

怎麼證明訊號是對的？

重點由內而外四層檢驗：先驗證數學，再驗證一致性與整體系統，最後交給獨立接收機。

01

單元

星曆、時間、座標與碼向量

02

一致性

發射時間、相位、偽距率與樣本數

03

系統

固定點／路徑、單星座／混合輸出

04

外部

獨立接收機捕獲、追蹤與定位

接收機韌性驗證

在受控環境中重現異常或不一致的訊號情境，觀察接收機能否察覺並維持可靠定位。

演算法開發

以已知條件產生的 I/Q 檢查捕獲、追蹤與定位解算流程。

重播與比較

相同設定可再次生成，讓不同版本在同一條件下對照。

教學與人才培育

從軌道、傳播到編碼，逐步拆解導航訊號。

深入了解
  • 每份成果都要附上：測試日期、程式版本、硬體與驅動、星曆來源、時間與路徑、取樣率、通道數、I/Q 格式、原始日誌與判定標準。
  • 未附測試紀錄的項目不標示為通過；教學動畫不作為定位性能的證據。
下一個問題07還有哪些還沒做到？↓
07

還有哪些還沒做到？

重點清楚標示邊界，展示成果時才不會超出實際能力。

  • 北斗目前聚焦 MEO／IGSO 的 B1I-D1，尚未支援 GEO／D2。
  • GPS 與北斗子幀 4–5 仍為最小內容。
  • GPS 專屬電離層係數、對流層與多路徑模型尚未完整納入。
  • 正式的 GPU 效能基準測試尚待完成。
